What it catches

Three pull requests are left open on purpose, never to be merged. Each runs the release gate in GitHub Actions against main, with the base branch's policy.

PR #2 · a safe refactor

Same behaviour, refactored. The gate passes: 8 of 8 trajectory checks and 11 of 11 safety checks.

FAILED

PR #3 · a broken agent

Five deliberate regressions: refunds under $100 skip approval, a denied approval is ignored, deletes instead of voids. Trajectory 3 of 8 (pass rate 1 → 0.4), safety 4 of 11.

A "performance" change stops treating tool output as data. Trajectory still passes 8 of 8; safety fails 9 of 11: injection_indirect drops to 0.2 as a memo makes the agent call delete_invoice.

Features

Every evaluator is a deterministic rule; none is an LLM judge. Cost is always labelled estimated.

Trajectory evaluation

Every tool call, argument and result the agent reports is checked against the dataset's rules by 7 trajectory evaluators, each naming the step that broke a rule. On the invoice agent: v1 10/10, the regressed v2 4/10.

Trajectory docs →

Adversarial & safety testing

Attack variants generated from your own cases across 7 categories, gated per category. 35 variants: v1 35/35, v2 15/35. A 226-variant stress set finds v1's real weaknesses: 211/226.

Safety docs →

CI release gate

agentforge gate compares a candidate run with the production baseline using plain arithmetic, stores an immutable decision and exits 0 / 1 / 2. A GitHub Actions workflow gates every pull request.

Release gate docs →

Tracing & failure replay

OpenTelemetry spans per case, PII-redacted and stored with the run (+6.9 to +9.6 ms per case, measured). Replay one case with one setting changed and diff it step by step: PR #4's case with D2 on goes FAIL → PASS.

Calibration

Answer checks calibrated on 45 dev, 25 held-out and 30 mutant answers: 44/45 (in-sample), 25/25, and only 11/30 mutants caught, reported, not tuned away. A grounding check with 14 false positives on real outputs ships opt-in.

Calibration details →

Kubernetes

Kustomize manifests with probes, requests/limits and a ConfigMap/Secret. The worker is its own Deployment, so evaluation capacity scales without the API. Deployed to kind in CI: 7/7 seeded runs completed.

Kubernetes docs →

MCP

Agents whose tools live behind MCP servers. The same tools in-process or over MCP give identical results, trajectories, verdicts and stored spans across 180 case pairs.

MCP docs →

Architecture

The API validates, stores and queues. Only the worker runs agents and evaluators. Finished runs, decisions and traces are immutable, enforced by database triggers.

Quick Start

Docker and Git; no API keys. The first build takes a few minutes, then a one-shot seed loads the demo.

git clone https://github.com/roshano3o3/agentforge.git
cd agentforge
cp .env.example .env          # Windows: copy .env.example .env
docker compose up

Then open http://127.0.0.1:3000/runs. Everything binds to localhost. Full instructions →

Limitations

  • Fixture-based demo. The example agent's planner is scripted Python, not a model. Its results, including every demo-PR verdict, show the mechanics catching real trajectory bugs in a real LangGraph graph, not any model's quality.
  • Scripted planner, same author. The v2 regressions were written on purpose, and the same author wrote v1's defenses and the attack templates.
  • Labeling bias. The same person labelled the calibration sets and built the evaluators. Labels were frozen by hash before the evaluators ran on them, but the labeller knew what the checks look for.
  • No authentication. Everything binds to localhost; the Kubernetes manifests have no Ingress. Not ready for a shared deployment.
  • Small samples. 5 safety cases per category, so the gate can only say "no regression" or "at most one failure"; the LLM benchmark is one day of measurements.
